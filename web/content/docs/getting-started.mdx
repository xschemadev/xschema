## Framework vs Runtime

xschema has two modes: **framework** and **runtime**.

### Framework

The full xschema experience. Define schemas in config files, run the CLI to generate native validators, use the typed client at runtime.

- Config-driven schema discovery
- Namespaces to organize schemas
- Generated code with full type inference
- Runtime client for typed schema lookups

```jsonc title="user.xschema.jsonc"
{
  "$schema": "https://xschema.dev/schemas/typescript.jsonc",
  "schemas": [
    {
      "id": "User",
      "adapter": "@xschemadev/zod",
      "sourceType": "file",
      "source": "./user.json"
    },
    {
      "id": "Config",
      "adapter": "@xschemadev/zod",
      "sourceType": "url",
      "source": "https://api.example.com/schemas/config.json"
    },
    {
      "id": "Settings",
      "adapter": "@xschemadev/zod",
      "sourceType": "json",
      "source": {
        "type": "object",
        "properties": {
          "theme": { "type": "string", "enum": ["light", "dark"] },
          "notifications": { "type": "boolean" }
        },
        "required": ["theme"]
      }
    }
  ]
}
```

### Runtime

Use adapters programmatically. You pass JSON schemas, you get generated code back. The CLI handles the conversion, but you control fetching, bundling, and output.

- No config files
- You handle schema fetching and `$ref` resolution
- Useful for libraries, custom tooling, or specific injection patterns

<Tabs groupId="language" items={["TypeScript", "Python"]}>
  <Tab value="TypeScript">
    ```typescript
    import { execSync } from "node:child_process";

    const schemas = [
      { namespace: "user", id: "User", schema: userJsonSchema },
      { namespace: "user", id: "Post", schema: postJsonSchema },
    ];

    const input = JSON.stringify(schemas);
    const output = execSync(`bunx @xschemadev/zod`, { input });
    const results = JSON.parse(output.toString());

    // results[0].schema = "z.object({ ... })"
    // results[0].type = "{ name: string }"
    ```
  </Tab>
