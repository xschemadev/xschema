xschema's core philosophy: **do the hard work upfront so adapters stay simple**.

## Design Principle

The CLI handles all complexity—ref resolution, draft normalization, validation—before adapters ever see a schema. Adapters receive "easy" input: self-contained, normalized schemas ready for straightforward code generation.

This separation enables:
- **High compliance** - Adapters don't need to implement $ref resolution or handle different drafts
- **Consistent behavior** - All adapters process identical bundled schemas
- **Simple adapter development** - Focus only on code generation, not schema processing

## The Pipeline

```
┌─────────┐    ┌───────────┐    ┌───────────┐    ┌───────────┐    ┌──────────┐
│  Parse  │ -> │ Retrieve  │ -> │  Process  │ -> │ Generate  │ -> │  Inject  │
└─────────┘    └───────────┘    └───────────┘    └───────────┘    └──────────┘
     │              │                │                │                │
  configs       raw schemas     bundled schemas   adapter code    output files
```

### 1. Parse

Discovers config files in your project by scanning for files with the xschema.dev `$schema` URL. Extracts schema declarations—ID, source type, adapter—and detects the target language.

```jsonc
// user.xschema.jsonc - namespace defaults to "user"
{
  "$schema": "https://xschema.dev/schemas/typescript.jsonc",
  "schemas": [{ "id": "Profile", "adapter": "@xschemadev/zod", "sourceType": "file", "source": "./profile.schema.json" }]
}
```

### 2. Retrieve

Fetches raw schemas from their sources—local files, URLs, or inline JSON. Handles HTTP headers with environment variable substitution for authenticated APIs.

### 3. Process

The heavy lifting happens here:

1. **Extract refs** - Discover all external `$ref` URIs in each schema
2. **Fetch externals** - Recursively fetch referenced schemas
3. **Validate** - Check schemas against JSON Schema meta-schemas
4. **Bundle** - Resolve all `$ref` pointers, embed definitions, produce self-contained schemas
5. **Normalize** - Convert any draft (3, 4, 6, 7, 2019-09) to draft 2020-12

After processing, schemas have no external dependencies—every `$ref` points to a local `$defs` entry.

### 4. Generate

Calls adapter CLIs via stdin/stdout. Adapters receive a JSON array of bundled schemas and return generated code:

```typescript
// Adapter receives:
[{ namespace: "user", id: "Profile", varName: "Profile", schema: { /* bundled, normalized */ } }]

// Adapter returns:
[{ namespace: "user", id: "Profile", varName: "Profile", schema: "z.object({...})", type: "{ name: string }", imports: [...] }]
```

### 5. Inject

Writes the generated code using language-specific templates. Creates the output file (e.g., `.xschema/xschema.gen.ts`) and a manifest to track which schemas were generated.

## Why Adapters Are Simple

Because the CLI handles:

| Complexity | Handled By |
|------------|------------|
| External `$ref` resolution | Processor (bundler) |
| Circular `$ref` handling | Processor (bundler) |
| Remote schema fetching | Retriever + Processor |
| Draft differences (items vs prefixItems, etc.) | Processor (normalize) |
| Meta-schema validation | Processor (validator) |

Adapters only need to:
1. Walk the bundled IR (intermediate representation)
2. Emit native code for each node type
3. Return the code string and type expression
