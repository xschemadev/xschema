Runtime mode gives you programmatic access to the xschema conversion pipeline. Feed it JSON schemas, get back adapter output — code strings, type expressions, and imports — ready to use in codegen, tooling, or dynamic validation scenarios.

```typescript
import { convert } from "@xschemadev/runtime";
import { adapter } from "@xschemadev/zod";

const results = await convert(
  { namespace: "user", id: "User", schema: { type: "object", properties: { name: { type: "string" } } } },
  { adapter }
);

console.log(results[0].schema); // "z.object({ name: z.string().optional() })"
console.log(results[0].type);   // "z.infer<typeof user_User>"
```

Under the hood, `convert` calls the xschema CLI as a subprocess. The same conversion logic, bundling, and compliance guarantees from framework mode apply here — you're just invoking it programmatically instead of through config files.

## When to Use Runtime Mode

| Use Case | Recommended Mode |
|----------|------------------|
| Schemas known at build time | [Framework](/docs/getting-started/typescript) (build-time) |
| Dynamic schemas from an API | **Runtime** |
| Schema registry integration | **Runtime** |
| Multi-tenant apps with custom schemas | **Runtime** |
| Codegen tools and CLIs | **Runtime** |
| Prototyping / REPL usage | **Runtime** |

## Framework vs Runtime

| Aspect | Framework (Build-time) | Runtime |
|--------|------------------------|---------|
| TypeScript types | Full inference | Generic types |
| Bundle size | Tree-shaken, minimal | Includes converter |
| Performance | Zero runtime overhead | Conversion cost per schema |
| Schema discovery | Config files | Programmatic |
| Output format | Generated source files | Code strings (ConvertResult) |
| Compliance tested | Yes | Yes (same pipeline) |

<Callout>
Framework mode is the right default for most apps. Use runtime mode when schemas aren't known until your code runs, or when building tools on top of xschema.
</Callout>
