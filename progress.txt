## Codebase Patterns

### Type probe infrastructure (shared pattern for zod + arktype)
- probe fixture lives in `typescript/packages/adapters/<adapter>/type-probe/` (has its own tsconfig for tsc resolution)
- `tasks/type-fidelity-baseline/<adapter>/generate-probe.ts` generates probe-fixture.ts by calling the adapter's convert()
- `typescript/packages/adapters/<adapter>/type-probe/extract-types.ts` uses TS compiler API to extract inferred types
- baseline artifacts go in `tasks/type-fidelity-baseline/<adapter>/`
- after generating, copy probe-fixture.ts into the type-probe/ dir before running extract-types

### Property name sanitization in pydantic adapter
- `_PYTHON_TYPE_BUILTINS` contains generic types that would break type annotations if used as field names
- Only includes types actually used in generic annotations: list, dict, set, tuple, type, frozenset
- Regular builtins like id, str, int are NOT included - they don't break annotations
- `_is_valid_python_identifier` rejects names in `_PYTHON_TYPE_BUILTINS`
- `_sanitize_property_name` renames them with underscore suffix (e.g., list -> list_)

## Task 1: Fix field name shadowing Python builtins - COMPLETED

**Problem**: Properties named "list", "dict", "set", "tuple", "type", or "frozenset" shadow Python's builtin types, causing type annotation errors like `'NoneType' object is not subscriptable` when evaluating `list[int]`.

**Solution**:
- Added `_PYTHON_TYPE_BUILTINS` frozenset in renderer.py with generic types used in annotations
- Updated `_is_valid_python_identifier` to reject these names
- Updated `_sanitize_property_name` to append underscore suffix
- Fields use `Field(alias="list")` to preserve JSON serialization

## Task 2: Fix additionalItems applicator scoping - COMPLETED

**Problem**: When using allOf with tuple schemas, the type guard check was `isinstance(v, list)` which failed to recognize tuples. After the first schema converts list→tuple, subsequent schemas in the intersection wouldn't validate.

**Root cause**: In `_type_guard_check_to_python`, the array check was `isinstance(v, list)` but tuple validators convert lists to tuples. When the intersection runs the second validator, it receives a tuple which doesn't match `isinstance(v, list)`.

**Solution**: Changed `_type_guard_check_to_python` for array check from `isinstance(v, list)` to `isinstance(v, (list, tuple))`.

**Location**: `renderer.py:2511`

**Compliance results**:
- additionalItems: 17/17 (draft4), 19/19 (draft6), 19/19 (draft7) - all 100%

## Task 4: Fix JavaScript pseudo-array handling - COMPLETED

**Problem**: Schemas with `items` as array (tuple validation) without `type: array` were failing when passed JavaScript pseudo-arrays like `{"0": "invalid", "1": "valid", "length": 2}`. Per JSON Schema, `items` only applies to arrays, not objects.

**Root cause**: In `converter.py`, `_is_array_only_schema` only checked for `kind == "array"`, but tuple schemas have `kind == "tuple"`. This meant no type guard wrapper was applied, so objects were incorrectly validated against tuple schemas.

**Solution**: Updated `_is_array_only_schema` to also check for `kind == "tuple"`:
```python
if ir_node.kind not in ("array", "tuple"):
    return False
```

**Location**: `converter.py:151`

## Task 3: Fix unevaluatedProperties uncle schema - COMPLETED

**Problem**: The intersection validator was mutating the value `v` by assigning the result of each validation. When Pydantic validates a dict, it returns a model instance. The next validator would then receive that model instance instead of the original dict, causing type mismatches.

**Failing test**: "property is evaluated in an uncle schema to unevaluatedProperties"
- Schema: nested `unevaluatedProperties: false` inside `foo.properties`, with `anyOf` at root defining `foo.faz`
- Test 1: `{foo: {bar: "test"}}` should be VALID - was failing because intersection chain broke
- Test 2: `{foo: {bar: "test", faz: "test"}}` should be INVALID - was passing for wrong reason

**Root cause**: In `render_intersection`, the line `v = validator_{i}.validate_python(v)` replaced the original dict with a Pydantic model. Subsequent validators couldn't validate the model instance from a different schema.

**Solution**: Changed intersection validator to NOT mutate `v`:
```python
# Before
v = validator_{i}.validate_python(v)

# After
validator_{i}.validate_python(v)  # Just validate, don't reassign
```

**Location**: `renderer.py:2081`

**Compliance results**:
- unevaluatedProperties: 25/25 (draft2019-09), 27/27 (draft2020-12) - all 100%
