## Task: fix-type-keyword (COMPLETED)

**Objective:** Fix remaining type keyword failures (was 83.8%, now 100%)

**Root Causes:**
1. **Boolean/integer confusion**: Python's bool is a subclass of int, so `isinstance(True, int)` returns True. Pydantic's default `bool` type accepts 0/1 as booleans.
2. **Type coercion**: Pydantic's default types coerce strings to numbers (`"1" -> 1`) and numbers to strings (`1 -> "1"`).
3. **Object type guard bug**: `_is_object_only_schema()` was always returning True for ObjectNode, even when schema had explicit `type: "object"`. This caused non-objects to incorrectly pass validation.

**Solution:**
1. Use Pydantic's strict types to prevent coercion:
   - `bool` → `StrictBool` (rejects integers 0/1)
   - `int` → `StrictInt` (rejects bools and strings)
   - `float` → `StrictFloat` (accepts both int and float, rejects strings)
   - `str` → `StrictStr` (rejects non-strings)
   - For constrained strings: `StringConstraints(strict=True, ...)`
2. Fixed `_is_object_only_schema()` to check for explicit `type` keyword in original schema
   - If schema has `type: object`, let Pydantic reject non-objects (correct behavior)
   - If schema only has object keywords without type, use type guard wrapper (filter semantics)

**Code Changes:**
- `python/packages/adapters/pydantic/src/xschema_pydantic/renderer.py`:
  - `render_boolean()`: Returns `StrictBool` instead of `bool`
  - `render_number()`: Uses `StrictInt` for integer, `StrictFloat` for number
  - `render_string()`: Uses `StrictStr` or `StringConstraints(strict=True, ...)`
- `python/packages/adapters/pydantic/src/xschema_pydantic/converter.py`:
  - `_is_object_only_schema()`: Now takes `original_schema` parameter and checks for `type` keyword
- `python/packages/adapters/pydantic/tests/test_renderer.py`:
  - Updated 15 tests to expect strict types

**Testing Results:**

## Task: fix-not-validation (COMPLETED)

**Objective:** Fix remaining not validation edge case (was 37/38, now 38/38)

**Root Cause:**
- Double negation test (`not: {not: {}}`) was failing
- The `render_not` function raised `ValueError('must NOT match')` inside a try-except block
- When nested `not` validators raised this error, the outer `not` would catch it via `except ValueError`
- The check `'must NOT match' in str(e)` would match the wrapped exception message
- This caused the outer `not` to re-raise instead of accepting the value

**Trace of bug:**
1. `not: {}` (inner) - empty schema matches everything, so negation rejects everything
2. Inner validator validates `"foo"` against `Any` → succeeds → raises "must NOT match"
3. `not: {not: {}}` (outer) catches this ValueError
4. Checks `'must NOT match' in str(e)` → True (Pydantic wraps the error message)
5. Re-raises instead of accepting → BUG

**Solution:**
- Restructured validator to use a `matched` flag instead of raising inside try-except
- Pattern: try/except sets flag, then check flag after block to decide action
- This avoids the trap of catching our own raised exception

**Code Changes:**
- File: `python/packages/adapters/pydantic/src/xschema_pydantic/renderer.py`
- Function: `render_not()` (lines ~1502-1520)
- Changed from:
  ```python
  try:
      validator.validate_python(v)
      raise ValueError('must NOT match')  # caught by our own except!
  except ValueError as e:
      if 'must NOT match' in str(e):
          raise  # problematic for nested not
      return v
  ```
- Changed to:
  ```python
  matched = False
  try:
      validator.validate_python(v)
      matched = True
  except Exception:
      pass
  if matched:
      raise ValueError('must NOT match')
  return v
  ```

**Testing Results:**
- ✅ not: 100% (38/38 passing, 2 unsupported due to unevaluatedProperties)
- ✅ All 85 pydantic adapter unit tests pass
- ✅ All 79 core package unit tests pass

**Key Insight:**
- Never raise inside a try-except if you plan to catch that exception type
- Use flags to separate "did it succeed" from "what to do about it"
- Pydantic wraps exceptions, so string matching on error messages is fragile

## Task: fix-items-validation (COMPLETED)

**Objective:** Fix items keyword validation (was 82.8%, now 100%)

**Root Causes:**
1. **Composition keywords ignoring siblings**: When parser encountered `allOf`, `anyOf`, or `oneOf`, it returned early without processing sibling validation keywords like `items`, `properties`, `type`. This meant a schema like `{allOf: [{prefixItems: [{minimum: 3}]}], items: {minimum: 5}}` would only apply the allOf, ignoring the items constraint.

2. **Fixed-size tuples for items:false**: When `prefixItems` was combined with `items: false`, the renderer generated a fixed-size tuple type `tuple[T1, T2, T3]` which requires exactly 3 elements. But JSON Schema says `items: false` means "no items beyond prefix", not "exactly N items required". Valid inputs: 0, 1, 2, or 3 items.

**Solution:**
1. **Core parser fix**: Modified `_parse_with_ctx()` to detect when composition keywords have sibling validation keywords. When both are present:
   - Parse the composition schemas into their nodes
   - Parse the remaining keywords as a separate schema
   - Wrap everything in an IntersectionNode

2. **Renderer fix**: Modified `render_tuple()` for `rest_items is False` case:
   - Generate custom validator that allows 0 to N items (where N = len(prefixItems))
   - Validate only items that exist against their corresponding prefixItem schema
   - Reject arrays longer than N items

**Code Changes:**
- File: `python/packages/core/src/xschema_core/parser.py`
  - Added sibling validation detection in `_parse_with_ctx()`
  - When composition + validation keywords coexist, create combined IntersectionNode
- File: `python/packages/adapters/pydantic/src/xschema_pydantic/renderer.py`
  - Modified `render_tuple()` for `rest_items is False` to generate variable-length validator
- File: `python/packages/adapters/pydantic/tests/test_renderer.py`
  - Updated test_render_tuple_fixed to expect new validator structure

## Task: fix-format-validation (COMPLETED)

**Objective:** Fix format string validation (was 0/133, now 100%)

**Root Cause:**
- JSON Schema draft 2020-12 treats the `format` keyword as an **annotation by default**, not a validation keyword
- Format validation only occurs when explicitly enabled via the `format-assertion` vocabulary in the meta-schema

## Task: fix-ref-validation (COMPLETED)

**Objective:** Fix $ref validation (was 0%, now 89.9%)

**Root Causes:**

1. **Property names starting with underscore**: Pydantic doesn't allow field names starting with `_`. Properties like `$ref` were sanitized to `_ref` which Pydantic rejected.

2. **Dunder names**: Similarly, `__proto__` was being kept as-is after sanitizing `$` and other chars, but Pydantic doesn't allow `__` prefix.

3. **Forward reference + nullable syntax**: When making a forward reference nullable, `'T' | None` is invalid Python. The union must be inside the quotes: `'T | None'`.

4. **Unresolved refs**: `$ref: "#"` root self-references couldn't use the class type because the root schema might have no explicit `type`, meaning non-objects should pass.

**Solutions:**

1. Modified `_sanitize_property_name()` to prefix names starting with `_` with `f` (field):
   - `$ref` → `_ref` → `f_ref`
   - `__proto__` → `f__proto__`

2. Added `_make_nullable()` helper function that handles forward references:
   - `'T'` → `'T | None'` (keeps union inside quotes)
   - `StrictInt` → `StrictInt | None` (regular append)

3. Changed `render_ref()` for unresolved refs to return `Any` type instead of forward reference. JSON Schema semantics require accepting any value when schema has no explicit type.

**Code Changes:**
- File: `python/packages/adapters/pydantic/src/xschema_pydantic/renderer.py`
  - Added `_make_nullable()` helper function
  - Updated `_sanitize_property_name()` to handle underscore-prefixed names
  - Updated `render_ref()` for unresolved refs
  - Updated all places that append `| None` to use `_make_nullable()`

**Testing Results:**
- ✅ ref: 89.9% (71/79 tests passing)
- ✅ properties: 96.4% (27/28) - up from 0% 
- ✅ Overall draft2020-12: 96.8% (1006 passed)
- ✅ All 85 pydantic adapter unit tests pass
- ✅ All 79 core package unit tests pass

**Remaining Failures (8 tests):**

**Key Insights:**
- Pydantic has strict field naming rules that differ from JSON Schema property names
